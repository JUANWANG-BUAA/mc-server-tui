# UI 专项评审：视觉层级与交互确定性

> 日期：2026-10-19。范围：`mc-tui`，不含官网重设计。
> 延续[严格产品化评审](PRODUCTIZATION_REVIEW.md)的聚焦、整合体验与质量门槛；属于独立分析，不是 Apple 官方标准。
> 方法：读取当前渲染、输入、工作区代码，查看三张已有截图，并对照历史体验报告。本次没有运行新的 GUI/PTY 实测；截图观察、代码结论、待验证假设分别标明。建议尚未实施。

## 1. 总判断

**当前 UI 已经有统一配色和丰富操作，但信息架构仍明显围绕命令、任务和内部状态展开。下一步应建立清晰的“实例 → 当前结果 → 下一步行动”层级，并消除输入、焦点与异步状态的不确定性。**

视觉问题主要是注意力分配：边框、强调色、活动卡、状态坞和底部提示都在表达重要性。交互问题主要是模式复杂：会话、经典面板、实例页、任务页、工作区、弹层和控制台需要用户记住不同规则。

一个截图可以显得整齐，却仍然让用户不知道正在操作哪台服务器；一个动作可以在代码里正确执行，却因为反馈位置和措辞不清而显得失败。两层必须共同验收。

## 2. 已有优点应当保留

- 渲染已有统一 `theme`、`ui` 和任务展示辅助模块，适合收敛语义而无需重写框架。
- 创建向导有明确步骤；版本和 Java 可以选择，避免手工录入技术标识。
- 下载展示真实字节与来源；已有取消、历史查询和断连保留状态的设计。
- 命令补全、历史、光标移动、命令面板为熟练用户提供效率入口。
- 状态包含文字与符号，紧凑布局会减少部分装饰，已有渲染测试基础。
- 恢复有预览和明确确认；关闭 TUI 不等于关闭服务器，底层生命周期边界合理。

优化应增强这些能力的可理解性。无需为了“焕新”更换 UI 技术或整体推翻会话模式。

## 4. 视觉层：从“很多信息”到“明确答案”

### 4.1 建立四级信息优先级

| 优先级 | 内容 | 表达规则 |
| --- | --- | --- |
| 第一层：当前对象与结果 | 实例名、运行状态、必须处理的失败 | 固定位置、强文字层级，不能被日志滚走 |
| 第二层：当前行动 | 下一步、执行中的任务、恢复影响 | 靠近相关内容；一个主要行动，其余为次要入口 |
| 第三层：支持判断的信息 | 版本、加入方式、最近备份、必要资源提示 | 可读且稳定，依据场景呈现 |
| 第四层：深入证据 | UUID、PID、完整路径、事件序列、hash、事务细节 | 按需查看、便于复制，不占正常路径主视觉 |

“次要”不等于低到难以辨认的灰色。用户完成任务必须阅读的说明，尤其错误原因、许可入口和生效条件，应保持足够可读性。

### 4.2 减少同时争夺注意力的容器

当前全局栏、shell 头部、活动卡、composer、状态坞和 footer 同时存在。每个区域都有理由，但组合后的成本没有被限制。

建议统一分工：全局栏只负责当前位置；实例摘要提供当前事实；主区域承载正在完成的任务；底部只负责当前焦点和少量操作提示。相同进度可在摘要和详情分别展示，但不能在同屏反复展开成多个重型区域。

80×24 的方案约束建议：保留一个主要内容区；普通活动摘要控制在 1–2 行，用户进入任务详情后再展开；焦点提示与普通快捷键合并；大面积边框仅用于需要界定操作范围的面板。具体行数须通过所有关键状态的渲染验证，不能机械删到重要信息消失。

### 4.3 颜色必须有语义

现有 `theme.rs` 已有 background、surface、text、muted、dim、accent、success、warning、danger 等 token。下一步需要明确使用约束，而非继续新增配色：

- accent 用于可操作焦点或当前步骤，不同时装饰路径、计数、版本、边框和所有快捷键。
- success 用于已经成立的结果；已受理、候选地址、未经验证的备份不使用成功结论。
- warning 用于需要注意的条件，danger 用于失败或破坏性操作影响；不要把整个长段落全部染红。
- 焦点、选中项、推荐值、禁用状态分别表达。推荐值不能冒充当前焦点。
- 必要文本可采用至少 4.5:1、关键非文本指示至少 3:1 的内部对比度目标；这是借用可访问性实践的设计目标，不是 TUI 已获得 WCAG 合规认证。

本次没有测量所有主题对比度，不将“历史截图感觉暗”写成当前所有主题均不合格。应对实际前景/背景组合计算，并在真实终端、`NO_COLOR` 和低色彩环境中验证。

### 4.4 终端排版要按单元格而非字符数设计

TUI 无法可靠控制用户字体，不能把字体大小层级当作主要手段。使用行距、对齐、有限粗体、语义前缀和列布局建立层级。

统一宽度计算、截断与光标定位；测试中文、ASCII 混排、组合字符和 emoji。字符宽度与字素编辑是两个问题：正确计算列宽不代表 Backspace 能正确删除完整用户感知字符。

长路径可以省略中间部分并提供完整查看；实例名可截断展示，但任何危险确认必须能辨认完整目标。时间优先本地时间，恢复列表同时保留明确日期，不能只显示容易歧义的“刚刚”。

### 4.5 品牌与装饰服从空间预算

Steve 吉祥物和主题可以带来亲切感，但不应在重要失败、恢复确认或窄屏中占据关键说明的位置。当前常规状态坞为吉祥物分配 11 列、5 行区域，应将其当作有成本的可选内容。

暂不新增主题。先为默认主题、无彩色表现和焦点语义建立统一验收，再维护其他主题。旧主题名和用户配置若调整，需要兼容迁移；视觉判断不是直接删功能的授权。

## 5. 交互层：一个动作必须有可预测的结果

### 5.1 默认围绕实例，而非围绕内部任务

建议采用“实例上下文 + 会话工作区”的方向：保留熟练用户的命令效率，在会话顶部持续展示当前实例和状态，主行动按状态改变。

| 场景 | 用户应先看见 | 主要行动 |
| --- | --- | --- |
| 没有实例 | 可以创建什么、环境是否缺项 | 创建服务器 |
| 已安装未启动 | 名称、游戏版本、尚未启动 | 启动 |
| 启动中 | 当前阶段、等待原因、失败时入口 | 查看启动日志 |
| 已就绪 | 就绪事实、加入说明、网络验证范围 | 查看/分享加入信息 |
| 启动失败 | 简明影响、证据摘要 | 检查原因 |
| 已停止 | 最近运行结果、备份情况 | 启动；备份为次要动作 |
| 恢复预览 | 时间、目标、覆盖影响 | 进入明确确认 |

主行动不必强制变成一个“按钮”；可以是可聚焦操作或一致的快捷入口。不要让 `Enter` 的默认作用随后台状态变化而偷偷更换；实时状态更新不能夺走输入焦点。

会话与经典面板不应长期形成两套不同业务行为。短期保留兼容，统一动作和事实来源；是否更换默认视图，先用相同任务做用户比较。

### 5.2 管理命令与控制台命令的目标必须可见

当前双用途输入框有速度优势，也有模式成本。建议在输入框旁明确显示“管理命令”或“发送到〈实例〉控制台”，切换实例时重新展示目标。

低风险查询可以快速执行；对补全出来的停服、权限修改等操作，优先填入完整命令或进入明确操作流程，再由用户提交。已明确输入的普通命令不必一律叠加确认，避免确认疲劳。

恢复、覆盖等危险行为的确认应绑定具体实例与计划，不能只依赖一个通用词。可以保留 `RESTORE` 输入机制，同时在输入附近展示实例、备份时间和覆盖范围；提交前由后端重新验证计划。

### 5.3 输入、导航和焦点规则要写成契约

| 操作 | 建议语义 |
| --- | --- |
| 普通字母 | 在编辑/搜索态输入文字；列表导航快捷键仅在非编辑态生效 |
| Tab / Shift-Tab | 在当前流程中切换字段；补全态如有不同语义必须就地提示 |
| Enter | 执行当前明确动作；有未填写参数时先引导填写 |
| Esc | 关闭最上层临时界面或退出当前编辑；不静默取消后台业务任务 |
| 返回/关闭页面 | 保留合理上下文；有未保存内容时说明去向；不停止服务器 |
| Ctrl-C | 当前代码定义为退出 TUI；必须说明影响并测试终端恢复，不可暗示它等于取消后台任务 |
| 多行粘贴 | 进入可检查的编辑缓冲，不能因换行自动执行多条命令 |

现有全局 Ctrl-B、Alt-Left/Right 等可能与终端编辑习惯、tmux 或宿主快捷键冲突，应验证并提供可发现的替代入口。输入中存在 `j/k` 被截获是明确错误；其他快捷键冲突需按环境记录，不能一概称为程序缺陷。

打开面板时焦点可预测，关闭后回到原输入位置；重新排序列表时按稳定 ID 保留选中对象，不能悄悄选中另一台服务器。

### 5.4 异步工作不能变成一个“请等待”的黑箱

异步反馈至少区分：请求已提交、已受理、执行中、结果已确认、失败、请求结果未知。连接中断不等于后台任务失败；已受理也不等于完成。

请求结果应绑定实例/任务身份，过时响应不能覆盖当前页面。任务完成后可以更新会话条目并追加必要历史；旧成功消息不能持续作为当前状态。

备份 busy 时禁止切页的现有行为说明 UI 生命周期仍与业务状态纠缠。目标是让用户可以离页、回来继续查看，并在全局看到重要完成/失败反馈。实现前必须先保证状态持久归属和重复提交控制，不能仅删掉拦截条件。

进度有真实总量才展示字节百分比；阶段进度注明阶段，不伪装成预计剩余时间。可取消性按任务和阶段判断，活动区域不能对所有任务泛化承诺“取消下载”。

## 6. 四个关键页面的改造简报

| 页面 | 保留 | 收敛 | 完成标准 |
| --- | --- | --- | --- |
| 会话首页 | 命令历史、快捷输入、实例摘要 | 合并重复状态与进度；突出当前对象、问题、主行动 | 用户不翻历史即可说明当前实例、状态和下一步 |
| 创建向导 | 三步结构、版本选择、EULA 明确接受 | 推荐值附原因，详细路径折叠；字段错误靠近字段，下一步始终可发现 | 无需解释 Java 路径即可完成；中文输入光标准确；失败保留草稿 |
| 实例详情 | 日志流、过滤、资源信息、控制台 | 摘要可收起；控制台与过滤输入模式可区分；日志暂停/追踪状态清晰 | 80×24 能有效阅读日志；新日志不打断回看；知道命令发给谁 |
| 备份恢复 | 备份校验、影响预览、显式确认 | 默认讲时间和世界影响，事务证据进入详情；确认与影响保持相邻 | 用户提交前能准确说出恢复到何时、覆盖什么、当前世界如何处理 |

任务详情作为第二层承接事件、hash 和来源。完成页先说明“安装了什么/失败在哪里/接下来做什么”，再提供展开执行记录；避免把每次进度更新都当成同等重要的事件。

## 7. 文案也是行为接口

| 当前表达类型 | 建议表达方向 |
| --- | --- |
| “分页目录” | 用户确实需要时显示“已显示 20 个，加载更多” |
| “journal / committed” | 默认说明“正在恢复世界；完成前请勿手动修改目录”，技术详情保留原术语 |
| “Task completed successfully” | 使用本地化的具体结果，如“扩展文件已安装，启动服务器后加载” |
| “Server is ready” | “服务器已就绪”；另行说明客户端/外网是否经过验证 |
| “正在执行恢复事务” | “正在恢复世界”，配真实阶段和对象 |
| “名称必须为 1–128 UTF-8 字节” | 默认解释可接受名称及当前输入过长；技术长度限制保留在详细说明 |

每句成功文案都必须得到实际结果支持；“已安装”不暗示“已加载”，“恢复完成”不暗示“已验证能进入游戏”。原始 Minecraft 日志可保持原文，产品自有状态应使用一致词汇。

## 8. 验证方式与优先顺序

### 第一批：修确定性问题并验证高风险输入

先处理 I-01、I-02，验证 I-03、I-05。测试完整搜索词、中文名称、未完整命令、连续 Enter、多行粘贴、切换实例后提交、断连后重试。对识别出的实际失败建立回归，未复现的风险继续标注。

### 第二批：重做 80×24 的注意力分配

只改默认主题下的会话首页、创建向导、实例日志和恢复确认四个场景。先统一状态/焦点语义和空间预算，再传播到其他主题和页面。记录前后画面及相同任务的操作路径。

### 第三批：解除不必要的流程锁定

围绕稳定实例/任务 ID 整理页面状态，保证异步结果、离页任务和重新进入的归属。验证草稿保留、日志位置、任务完成通知、返回焦点及关闭页面语义。

### 验收矩阵

| 维度 | 必测条件 |
| --- | --- |
| 尺寸 | 120×40、80×24、40×12；操作中改变尺寸 |
| 输入 | 纯键盘、可选鼠标、中文/英文混合、组合字符、长名称、多行粘贴 |
| 显示 | 默认主题、无彩色、低色彩终端；必要信息不依赖颜色 |
| 数据 | 空列表、多实例、长日志、并行任务、失败结果、旧响应晚到 |
| 生命周期 | 首次加载、刷新失败、断连重连、任务中切页、恢复确认取消 |
| 宿主 | macOS/Linux 的真实终端与 SSH；记录 tmux 和浏览器终端差异 |

渲染测试检查文本、布局和焦点坐标；状态测试检查动作与目标；PTY 检查终端输入和退出恢复；真实终端观察字体宽度、复制、粘贴和宿主按键冲突。截图通过不替代其他三类验证。

建议邀请 5 位目标用户，在关键页面短暂观察后解释“我操作谁、现在怎样、接下来做什么”；至少 4 位无需帮助答对，作为继续迭代的试验门槛。恢复确认要求每位参与者都理解对象和覆盖范围。小样本用于发现问题，不能证明总体可用性。

建议把本地按键到可见反馈 p95 不超过 100 ms 作为性能调查目标，必须报告硬件、终端、数据规模、样本量和网络条件；不将等待后端完成算成本地交互延迟，也不把此目标写成已有实测成绩。

## 9. UI 发布否决条件

- 当前实例不清楚，或输入/异步结果进入错误实例。
- 备份失败、未知网络状态被展示为已验证成功。
- 输入普通搜索文字触发导航，或粘贴/补全导致未经明确提交的有副作用操作。
- 在声明支持的正常尺寸中，危险操作目标和影响无法读取，却仍可直接提交。
- 加载失败无出口、切页丢失必须保留的输入，或返回后焦点落入不可预测位置。
- `NO_COLOR` 下无法识别关键状态，或真实终端退出后持续留在损坏输入模式。

其中当前已由代码确定的问题应先修；风险项需要复现与回归证据。发布判断与[产品化门槛](PRODUCTIZATION_REVIEW.md)共同执行。

## 10. 这轮 UI 工作的交付边界

交付一个更容易判断、输入更可靠、结果更可追溯的默认体验：四个关键页面、统一状态词汇、输入焦点契约、明确空间预算及相关回归证据。

暂不新增主题、不更换框架、不以重新命名所有组件代替改进，也不凭历史截图直接宣布旧问题已修或仍存在。最终以当前候选产物上的真实操作和前后对照结果验收。
