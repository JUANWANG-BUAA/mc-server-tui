# 工程优化指南：架构收敛与可验证重构

> 面向维护者、技术负责人及重构执行者。核对日期：2026-10-19。
> 基线：workspace 0.1.0、Rust 1.89.0、15 个 crate；以当前工作区及其未提交改动为依据。
> 本文规定后续优化的方法、顺序和验收标准。除明确标注的已完成项外，方案均未实施。

## 1. 优化目标与决策原则

优化的目标是降低一次业务变更需要理解和修改的范围，同时保持数据、进程和协议行为可预测。代码行数、文件数量与 crate 数量只用于发现热点，不能单独证明工程质量。

一次重构至少应改善以下一项，并提供对应证据：

- **内聚性**：一个模块围绕同一个业务不变量变化，调用方不再依赖其内部步骤。
- **耦合度**：业务规则变化不再要求多个无关模块同步修改。
- **单一事实来源**：同一规则只有一个权威实现，其他位置通过调用或转换复用。
- **正确性**：用可重现的失败和回归测试证明缺陷被消除。
- **运维成本**：减少资源消耗、故障诊断时间或发布验证成本，提供前后测量。

决策顺序为：数据与进程安全 → 行为正确性 → 模块边界 → 可维护性 → 性能与体积。避免在同一变更里同时迁移协议、调整行为、搬动文件和升级依赖。

**DRY 针对的是知识重复。** 两段代码看起来相似，但采用不同安全策略或事务语义时，可以保持独立。只有它们表达相同规则、应当一起变化时，才需要抽取。

必须区分以下状态：

- **已确认缺陷**：有失败输入或明确违反契约的可达路径。
- **待验证风险**：实现暴露出问题可能性，还没有复现或验证适用条件。
- **结构性改进**：当前行为可用，但修改成本、职责或依赖关系需要收敛。
- **已完成**：修改、针对性验证、必要的兼容检查和文档同步均完成。

## 3. 架构边界：规则应该放在哪里

下表给出优化时应遵循的职责归属。它是边界约束，不是声称当前所有代码已经满足该分层。

| 模块 | 应拥有的职责 | 应避免引入的职责 |
| --- | --- | --- |
| `mc-core` | 领域值、协议数据、错误结构、无 I/O 的领域规则 | HTTP、SQLite、终端状态、万能工具集合 |
| `mc-config` | 配置格式、覆盖优先级、平台路径、配置持久化 | 连接 daemon、安装系统服务、业务任务执行 |
| `mc-client` | socket 帧、超时、协议协商、类型化请求响应 | 再定义默认路径、实现建服和备份规则 |
| `provider-paper` | Paper 元数据与构建解析 | 实例注册、UI、通用文件事务 |
| `mc-download` | 产物下载、来源约束、校验、缓存与续传 | 游戏业务选择、直接修改已安装实例 |
| `mc-instance` | 实例配置与锁定元数据、安装、索引与恢复 | 终端交互、runner 通信策略 |
| `mc-task` | 任务持久化、事件、准入、执行限制与取消信号 | 每一种业务任务的完整实现 |
| `mc-supervisor` | 进程身份、runner、生命周期、停服租约、控制台与日志 | UI 文案、整合包解析 |
| `mc-backup` | 世界备份、清单校验、恢复计划与恢复事务 | 自行停止 Java、实现 TUI 确认流程 |
| `mc-modpack` | 当前的整合包分析；后续可承接稳定的包语义 | 在分析阶段写实例、运行包内脚本 |
| `mc-system` | Java 和宿主环境探测 | 业务编排、终端渲染 |
| `mc-daemon` | 请求适配、能力检查、服务组装、用例编排 | 长期承载所有上游解析、文件规则和算法 |
| `mc-cli` / `mc-tui` | 输入、交互状态、展示、通过 client 调用服务 | 直接操作实例数据库、绕过 supervisor 管理进程 |
| `mc` | 用户入口、setup、服务管理、安装版本选择 | 复制 daemon 的业务实现 |

新增依赖前检查 `cargo tree -p <crate> -e normal` 和 `cargo tree -i <dependency>`。生产依赖与 `dev-dependencies` 分别评估；测试 fixture 引入的反向依赖不能直接视为生产架构倒置。

抽取顺序为：私有函数 → 同 crate 的业务模块 → 稳定的内部接口 → 必要时独立 crate。跨 crate 抽取需要解释复用方、依赖方向及 API 所有权，不因文件超过某个行数就拆 crate。

## 4. 如何提取抽象而不制造新负担

### 4.1 抽象的准入条件

每个新抽象必须回答五个问题：

1. 它统一的是哪条业务规则或资源生命周期？
2. 哪些调用方需要相同语义，哪些差异必须保留？
3. 输入、输出、错误和副作用是否可从接口直接理解？
4. 规则变化后是否只需修改一个权威实现？
5. 与保持局部实现相比，它是否减少了调用方必须理解的概念？

已有 `ManagementSource` 是适合保留的隔离点：应用状态不必理解 socket 通信，测试可以注入来源。不要为了“接口化”给所有结构体套 trait；多实现、测试替身或真正可替换的边界才是理由。

### 4.2 本项目的具体应用

| 候选 | 合理的收敛方式 | 必须保留的差异 |
| --- | --- | --- |
| `Config::load` 与 `load_from` | 一个读取实现，另一个只解析配置路径并委托 | 环境覆盖顺序、缺失文件与读取错误的区别 |
| 多视图的状态/进度格式化 | 先检查并复用 `task_presentation.rs`、`ui.rs` | 页面布局、用户操作入口和交互语义 |
| 下载字节计数、校验、进度 | 用明确的下载策略与校验类型承载共同能力 | Paper 与 Modrinth 的 hash 算法、host、重定向、代理和缓存策略 |
| 包分析与导入中的路径/兼容判断 | 共享纯解析结果或策略对象 | 预览可解释拒绝原因；应用必须重新验证当前文件系统 |
| runtime 中重复请求调度 | 先明确请求身份、结果归属、单次在途和 pending 语义 | 查询合并与写命令提交不同；取消 UI 等待不等于取消任务 |

通用 `utils.rs`、大量布尔参数、字符串开关和无类型事件总线都容易隐藏边界。优先采用语义明确的函数、枚举和业务模块。

## 5. 优先工作包与验收标准

优先级依据后果、触达范围、证据强度和验证成本排序。P0 表示先调查的数据/兼容风险，**不表示已经确认存在 P0 缺陷**。

### P0-A：配置读取与保存的可靠性

**证据**：[mc-config/src/lib.rs](../crates/mc-config/src/lib.rs) 中 `load`/`load_from` 重复读取逻辑；`is_file()` 分支将不满足条件的路径按默认配置处理；`save_to` 使用固定 `toml.tmp` 路径，写入后才设置权限，没有显式文件同步。

**待验证问题**：并发保存是否互相干扰；目录、不可读路径和损坏 TOML 的错误是否被正确区分；写入/rename 失败后是否残留临时文件；相对配置路径是否正常。不能把 rename 的原子可见性直接等同于断电持久性。

**实施顺序**：

1. 用临时目录和隔离测试复现边界，只对 `NotFound` 使用默认值；明确是否支持配置文件符号链接。
2. `load()` 委托 `load_from()`，保证环境覆盖只应用一次。
3. 使用同目录、独占创建的临时文件，创建时设置私有权限；按持久化契约处理 flush、文件同步、rename 和目录同步。
4. 由所有权清晰的清理机制处理失败残留。唯一临时文件只能消除写入相互破坏，不能解决业务层读改写的丢失更新；如有多写者要求，另行设计锁或版本比较。

**验收**：错误路径不静默变默认值；原配置在提交前失败时仍可读；成功后 TOML 完整；失败后临时文件清理符合约定；Unix 权限符合契约；并发测试按明确的写者策略验收。

### P0-B：公开 API 删除与旧版本行为

**证据**：前一轮删除了公开导出的 `mc_client::default_socket_path`，仓库内没有调用者。

**实施要求**：检查该 crate 是否被对外发布、下游项目是否使用此导出，以及发行说明中的兼容承诺。仓库内零引用不是外部零消费者的证明。

**决策**：若仅供 workspace 内使用，记录结论；若需要保持 Rust API 兼容，提供委托到配置层的弃用包装并给出迁移周期。判断时保留原 API 的“平台默认路径”语义，不随意改成读取环境配置。

**验收**：全 workspace 编译通过；支持的外部调用方式有明确迁移说明；API 8–9 的 wire 协商及任务过滤不受 Rust 内部整理影响。删除一个直接依赖不等于整个 release 已移除该传递依赖，体积变化需要测量。

### P1-A：TUI 状态归属与事件处理

**证据**：[app.rs](../crates/mc-tui/src/app.rs) 同时包含工作区、详情缓存、会话编辑、页面可见性、请求意图和命中测试；[runtime.rs](../crates/mc-tui/src/runtime.rs) 有多个 channel、在途标记和 pending 标记。

**建议步骤**：

1. 列出状态表：字段的拥有者、生命周期、谁能写、是否跨页面保留、异步结果如何匹配。
2. 先按 shell 编辑、导航、任务、实例等职责整理私有模块；搬移完成后再独立进行状态封装。
3. 将真正互斥的界面状态表达为枚举；允许叠加的帮助/面板和持久缓存分别建模。
4. 缩小 `AppState` 可写表面，逐步通过领域方法更新子状态；仅拆成多个 `impl AppState` 文件不算完成封装。
5. 检查异步结果是否携带 instance/task/page 身份，必要时使用请求代数，防止切页后的旧响应覆盖当前状态。

**验收**：页面编号稳定、草稿和日志位置保留、关闭页不停止进程；重复刷新有界；旧响应不会串页；断连保留最后成功数据。相关状态测试、渲染测试和 PTY 流程通过。

### P1-B：daemon 下载与扩展职责

**证据**：[management/addons.rs](../crates/mc-daemon/src/management/addons.rs) 中 `Upstream` 负责 HTTP、元数据大小限制、流式 SHA-512 校验和进度；工作区已有 `mc-download`。这些实现有重叠，但安全策略不完全相同。

**建议步骤**：先编写策略对照表，覆盖来源、DNS、代理、重定向、校验、大小、取消、缓存与临时文件所有权，再决定哪些能力进入 `mc-download`。短期可先在 daemon 内分离 upstream transport 与扩展依赖解析，避免直接扩大公共 API。

**验收**：每种来源仍使用自己的信任策略；超限、hash 错误、取消和网络失败不提交产物；超时与进度仍可观察；业务代码不再复制同一传输规则。禁止为实现统一接口降低任何一条校验。

### P1-C：整合包分析与应用边界

**证据**：[mc-modpack/src/lib.rs](../crates/mc-modpack/src/lib.rs) 承担分析，[management/packs.rs](../crates/mc-daemon/src/management/packs.rs) 承担 ZIP/MRPACK 应用与导出。

**建议步骤**：比较两侧对 loader、路径、环境、文件限额和覆盖优先级的处理；提取可复用的包语义。由 daemon 组织停服租约和任务，由文件事务层管理 staging、提交和清理。

**验收**：同一输入的预览/应用拒绝原因一致；应用阶段重新检查文件系统；相同内容跳过、冲突不覆盖；世界、身份文件和核心文件不会被误写。先界定“预检无副作用”与“提交中断后如何恢复”，不可仅凭 staging 宣称完整事务性。

### P2-A：启动器与平台服务模块

**证据**：[mc/src/main.rs](../crates/mc/src/main.rs) 包含命令分派、setup、状态查询、版本回滚及路径处理；[service.rs](../crates/mc/src/service.rs) 包含 launchd/systemd 分支。

**建议步骤**：依照 setup、update、进程执行、展示等职责拆内部模块；平台实现提供小型统一接口，共享模型留在 service 边界。只有重复且语义相同的格式化/命令执行才合并。

**验收**：命令参数、退出码和 JSON 输出稳定；版本路径限制、回滚目标 schema 检查仍通过；两平台生成的服务单元正确；daemon 重启不影响 runner 的既有承诺。

### P2-B：历史产物与文档治理

**证据**：仓库同时包含 `site/assets/`、`output/playwright/`、根设计文档及脚本；README 当前引用了 `output/playwright` 图片。

**建议步骤**：先建立引用清单与文件用途，再分类为发布资产、验证证据、可再生输出、历史决策和用户文件。内容 hash 相同也只能作为候选，路径可能服务于独立部署。

**验收**：被删文件没有未迁移的运行、文档或发布引用；截图证据有保留位置或重建方法；官网发布目录完整；用户未跟踪文件未经归属确认不删除。禁止用全局 `git clean -fdx` 代替整理。

## 6. Bug 修复与重构的执行流程

每个工作包遵循以下闭环：

1. **定义不变量**：例如“关闭页面不终止 Java”“恢复失败保留原世界”。写出受影响的调用路径、协议和持久化边界。
2. **建立证据**：Bug 用失败测试或最小复现；结构改进记录重复规则、依赖边和修改范围。
3. **选择最小切口**：先纯函数/解析边界，再状态与 I/O 所有权；需要改变行为时与机械搬移分开。
4. **实现与迁移**：每个提交保持可构建；临时适配层指定删除条件，避免新旧流程永久并存。
5. **按风险验证**：先模块测试，再受影响的集成/协议/PTY，最后完成 workspace 门禁。
6. **对照验收**：记录解决了什么、保留了什么限制、有哪些未验证的平台条件。
7. **安排回退**：纯代码可以 revert；已写入的数据或新 schema 必须有额外恢复计划。不要把代码回退等同于数据回退。

遇到不相关失败，先确认是否由本次引入，再单独记录。若是影响安全或发布的已有失败，可以阻断交付，但不要悄悄扩展当前重构范围。

## 7. 异步、资源与数据安全底线

具体数值以 [异步并发契约](ASYNC_CONCURRENCY.md) 和实现为准；优化不能取消现有有界性。

- **执行边界**：同步文件扫描、压缩、hash 和 SQLite 工作不得长时间占用 Tokio worker。`spawn_blocking` 同样需要有界准入；future 被丢弃并不保证阻塞工作停止。
- **锁的所有权**：停服租约必须覆盖实际工作完成的时间，特别是迁移到阻塞 worker 后。明确锁顺序，不跨网络等待持有无关全局锁。
- **取消语义**：区分取消客户端等待、发出任务取消信号、任务确认取消和提交已完成。不可取消阶段需明确反馈。
- **任务一致性**：任务快照与事件的事务关系、事件序列和断连去重规则保持不变。daemon 重启后标记 interrupted 的策略不能被静默重放取代。
- **文件边界**：路径词法校验、符号链接策略和实际打开文件是不同环节；`canonicalize` 或 `starts_with` 单独不能消除检查到使用之间的竞态。
- **进程身份**：未验证身份的 PID 不能被信号、控制台或“修复”逻辑接管。生命周期必须经过 supervisor。
- **外部数据**：HTTP body、ZIP 展开、文件数、日志、任务结果和 UI 缓存必须有合理上限；声明大小不替代实际字节检查。
- **错误结构**：保留错误类别、可重试性和证据；避免把网络、解析、冲突和文件错误全部压成 Internal。日志使用实例/任务 ID 关联，凭据与敏感 URL 需要脱敏。

## 8. 测试与质量门禁

### 8.1 本地与 CI 的基础命令

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo build --workspace --locked
python3 scripts/check_protocol_window.py
git diff --check
```

修改 Cargo 依赖时，先通过正常 Cargo 命令更新并审查 `Cargo.lock`，再使用 `--locked` 验证。不要手改锁文件来掩盖依赖变化。`cargo machete` 可作为已安装时的辅助检查，目前不应描述为 CI 必有门禁；采用其报告前仍需检查 feature、宏和平台分支。

### 8.2 按变化选择验证

| 变化 | 最低针对性证据 | 需要补充的边界 |
| --- | --- | --- |
| 纯重命名/搬移 | 受影响测试、编译、diff 审查 | 可见性、`cfg` 分支和文档链接 |
| 配置/路径 | 读取失败、保存失败、权限、相对路径 | 并发写、环境隔离、平台行为 |
| TUI 状态/调度 | 状态转换、异步结果归属、渲染 | 80×24 与紧凑布局、键盘/鼠标、PTY |
| 下载/归档 | 超限、错误 hash、取消、非法路径 | 中途断开、临时文件清理、来源策略 |
| 生命周期/恢复 | 锁与身份、错误注入、恢复测试 | daemon 退出、进程重连、真实主机演练 |
| 协议/持久化 | 旧版本 fixture、版本拒绝、迁移测试 | 当前协议窗口、回滚及未知字段语义 |
| 删除文件/依赖 | 引用审计、构建与打包检查 | 文档、静态站点、外部消费者 |

TUI 按变化运行下列相关脚本，而非每次文档修改都启动完整场景：

```sh
python3 scripts/tui_pty_smoke.py
python3 scripts/tui_guided_create_pty.py
python3 scripts/tui_task_detail_pty.py
python3 scripts/tui_instance_detail_pty.py
```

脚本使用 fake daemon。它们不能替代真实 Minecraft 的进程、世界恢复和网络验证。详情见 [TUI 测试](TUI_TESTING.md)、[监督契约](SUPERVISION.md) 与 [备份恢复设计](BACKUP_RESTORE_DESIGN.md)。

测试优先断言外部可观察的不变量，不为简单转发函数逐行镜像实现。并发测试用同步信号控制交错；故障注入用隔离目录和测试依赖；环境变量测试避免并行污染。

## 9. 体积、性能与维护性如何度量

先保留基线再设置目标；以下指标尚未在本指南中给出实测值，不应承诺百分比收益。

| 指标 | 采样办法 | 如何使用 |
| --- | --- | --- |
| 一个用例的修改触达面 | 在相似需求中统计实际修改的生产模块和接口 | 判断职责是否收敛，排除机械移动造成的数量膨胀 |
| 重复规则数量 | 台账记录规则、权威实现、重复点与调用方 | 目标是规则单一来源，不追求文本重复率归零 |
| 依赖与 feature | `cargo tree -d`、`cargo tree -e features` | 解释重复版本/feature 来源，避免盲目统一版本 |
| 构建时间 | 相同工具链/target/profile；记录 clean 与 incremental，使用 `cargo build --workspace --locked --timings` | 区分缓存、网络、链接和代码变动影响 |
| 发布体积 | 比较同 target 的 release 二进制总量和压缩包 | 避免用 debug 产物判断最终体积 |
| 交互成本 | 固定实例/任务数量，记录按键到绘制延迟和请求量 | 优化轮询、分配或重绘前先定位瓶颈 |
| 常驻资源 | 区分 daemon、TUI、runner、Java 的 CPU/RSS，固定采样窗口 | 不把 JVM 内存误算成管理工具开销 |
| 故障恢复 | 记录注入点、残留资源、恢复步骤、耗时与结果 | 比较恢复能力而不是只看正常路径 |

每份性能记录包含 commit/worktree 状态、OS、硬件、Rust、target、profile、数据规模、运行次数、冷/热缓存条件与原始结果。小样本报告中位数和范围；足够样本再使用 p95。隔离 worktree/target 目录测冷构建，不清理开发者工作区来制造“干净环境”。

LTO、`strip`、`codegen-units`、allocator 更换、缓存和 unsafe 优化都需要单独实验。采用前同时评估构建速度、运行表现、崩溃诊断和平台兼容性。

## 10. 分批交付与长期防回退

按验收出口推进，不预设“大重构完成日期”：

| 批次 | 范围 | 出口条件 |
| --- | --- | --- |
| A：确立事实 | 基线、风险复现、外部 API 调查、资产引用清单 | 每项有证据、负责人、风险和验证方法 |
| B：低耦合切口 | 配置读取去重、可靠保存、确认无用的内部代码 | 有回归覆盖、兼容说明，所有基础门禁通过 |
| C：状态收敛 | TUI 状态归属、请求结果匹配、可见性控制 | 状态/PTY 验收通过，可写表面实际缩小 |
| D：服务边界 | 下载策略、整合包语义、启动器模块 | 重复规则消除，策略与事务测试保持或增强 |
| E：治理闭环 | 引用迁移、文档修正、指标复测、门禁补齐 | 清理有依据，收益可复核，无临时双实现遗留 |

一个 PR 以一个可解释的目标为单位；变化较大时，先提交不改变行为的准备工作，再修复或切换调用方。必要的架构决策记录包含背景、方案比较、选择、后果和撤销条件；只有依赖方向、公共接口或持久化语义等长期选择值得单独记录。

每次评审回答：

- 这次改变统一了哪条规则，还是仅仅移动了文件？
- 新抽象的拥有者、生命周期与错误语义是否明确？
- 是否扩大公开 API、引入反向生产依赖或新的隐式全局状态？
- 是否保留协议、实例格式、进程安全与资源上限？
- 测试能否捕获此次修复的失败，而非只验证实现细节？
- 被删内容的消费者是否全部核对，用户资产是否得到保留？
- 数据写入后的回退方案是否真实可执行？
- 性能、体积与“更简洁”的结论是否有证据？

## 13. 本轮执行记录（2026-10-19）

- **P0-A 已实施**：`load()` 委托 `load_from()`；只有路径缺失时使用默认配置，目录、非普通文件、损坏 TOML 和其他 I/O 错误都会返回错误。现有文件软链接按目标读取和保存，失效软链接返回错误。保存使用同目录 `create_new` 临时文件，Unix 创建权限为 `0600`，写入后同步文件、原子替换并同步目录；失败会清理未提交的临时文件，新建配置文件父目录权限为 `0700`。目录同步若在 rename 后失败，会明确报告“文件已替换但持久性未确认”，因此该错误不等价于原文件仍在。
- **并发语义**：独占临时文件避免并发写者互相覆盖临时内容；对同一配置的并发读改写仍采用最后完成 rename 的写入生效，不提供版本比较或丢失更新保护。
- **验证**：配置读写、错误路径、软链接、权限和失败清理有回归覆盖；`cargo fmt --all --check`、`cargo clippy --workspace --all-targets --locked -- -D warnings`、`cargo test --workspace --locked`、`cargo build --workspace --locked` 与 `python3 scripts/check_protocol_window.py` 均通过。
- **P0-B 决策**：仓库内没有 `default_socket_path` 调用者；`cargo info mc-client --registry crates-io` 未找到已发布 crate。按当前未发布的 workspace 用法，接受删除此导出和 `directories` 直接依赖。该查询不能排除外部 Git 依赖；首次公开发布 `mc-client` 或建立 Rust API 兼容承诺前，应重新评估，并在需要时加回委托到配置层的弃用包装。
- **TUI 输入安全跟进**：不完整 slash 前缀的第一次 Enter 现在只填入高亮完整命令，第二次 Enter 才执行；bracketed paste 会作为一个粘贴事件处理，多行内容折叠为空格并留在当前输入框供检查。fake-daemon PTY 已验证 `/sto` 第一次 Enter 不发 `stop_server` 请求、多行粘贴不发 `send_console_command` 请求，相关应用状态测试也通过。
