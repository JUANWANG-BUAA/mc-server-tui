# 严格产品化评审：聚焦、完整体验与发布否决标准

> 日期：2026-10-19。对象：mc-server-tui 当前开发工作区及其产品规划。
> 方法：借鉴通常与 Apple 产品实践相关的聚焦、整合体验、默认品质和细节一致性原则，作出针对本项目的独立判断。本文不是 Apple 内部流程、官方意见或经过其认证的标准。
> 状态：发展建议与拟议门槛，尚未实施或通过。采用本文意味着需要显式调整近期路线图；不代表现有功能已被移除、实验已完成或历史发布承诺已自动变更。

> **2026-10-20 状态补充：** 本文保留 10 月 19 日评审结论与证据边界。此后开发分支已加入
> 四字段 `server.properties` 编辑（MOTD、人数上限、难度、视距），并已将 FAQ、
> MRPACK 导入契约和协议文档同步到当前实现。2026-10-19 的本机 Paper 演练实际完成了
> 停服备份、校验、恢复和恢复后启动，但没有游戏客户端进入世界。当前协议为 8–11，
> 已加入协调停服/启动的受控重启；macOS workspace 测试为 213 项。这些工程进展仍不能替代真实客户端、异地玩家加入或
> 完整主旅程验收。下一里程碑的路线取舍也尚未正式决定。

## 1. 评审结论

**项目拥有值得保留的工程底座，但尚未拿出足以支撑“低门槛、可信赖的朋友服管理工具”这一承诺的完整产品证据。下一阶段应冻结功能面扩张，围绕一个真实用户结果交付。**

这个结果是：

> 一位会打开终端的服主，能够让朋友加入一个 Minecraft Java 服务器；下次回来仍能管理它；遇到常见问题知道怎么办；恢复世界时知道会发生什么，并能验证结果。

目前最需要警惕的，是用功能数量和界面丰富度替代完成度。Paper、Fabric、扩展、整合包、多页面、主题、玩家管理各自可以工作，不代表用户从安装到维护已经获得一致体验。

对下一版本的判断应非常严格：**能演示成功，不够；维护者在旁边指导才成功，不够；失败后只能读源码解决，不够；界面表示成功而实际结果尚未成立，直接判失败。**

## 2. 事实、推断与尚缺的证据

| 类别 | 当前依据 | 产品判断 |
| --- | --- | --- |
| 已有工程能力 | 常驻 runner、持久任务、下载校验、停服备份与恢复、协议兼容代码及测试 | 可以支撑可靠产品，不应为重写而重写 |
| 已有实际操作记录 | [体验报告](../output/playwright/player-review-20261019/体验报告.md) 记录真实 Paper 启动、控制台、备份、恢复和再次启动 | 不应再把项目描述成只有 fake daemon 验证 |
| 未闭合的使用证据 | 同一报告明确没有实际游戏客户端进入，也没有异地朋友加入 | 本机探测成功不能替代联机成功 |
| 已有体验改进 | 当前代码包含连接说明、任务结果反馈和扩展管理 | 历史报告中的问题必须复验，不能全部当作仍然存在 |
| 已有构建验证 | 本轮前序工作中的 workspace 测试、严格 clippy 通过；CI 配置有 macOS/Linux 矩阵 | 不等于真实 Linux 部署、恢复及升级验收已全部完成 |
| 能力表述存在版本歧义 | 当前开发分支具备 Fabric/导入能力，FAQ 和旧版说明仍主要描述 Paper/只读分析 | 必须分清源码、预发布和稳定版，先定位文档适用版本再纠正 |
| 重要旅程仍缺功能 | 尚无完整 `server.properties` 编辑、接管旧服、在线/定时备份闭环 | 不应宣传成覆盖完整服主日常维护 |

本文没有重新执行游戏客户端联机、远端发布包检查或竞品实测。竞争力、需求强度和发布质量的结论应保留对应证据边界。

## 3. 以产品公司视角提出的六个要求

### 3.1 聚焦：每一项“也支持”都要付出维护成本

下一阶段只服务一个明确对象：**会使用终端，希望和少量朋友玩 Java 版、管理一台主机上少量实例的服主。**

主验证场景建议选择 Linux 主机上的 Paper 朋友服；macOS 保留本地试服和准备场景，继续履行现有支持范围。平台宣传宽度必须与真实验证覆盖匹配，不能把交叉编译成功写成完整体验支持。

暂不把纯图形界面新手、Bedrock 玩家、复杂模组整合包作者、多租户服务商和商业服务器网络同时当成首批用户。

选择 TUI 就接受相应用户边界。没有证据时，不应一面承诺“所有新手都能用”，一面要求用户处理终端、Java 路径和 Unix 服务。若试用表明终端本身持续阻断目标人群，应收紧受众或独立验证图形入口，而不是不断增加 slash 命令说明。

### 3.2 对完整结果负责：用户不会替架构分层承担体验成本

用户只看到安装、开服、加入、维护。daemon、runner、任务队列和协议分层应在必要时可诊断，正常流程不要求用户理解它们。

例如“安装完成，但服务未启动；服务启动，但 Java 不匹配；Java 启动，但客户端不能加入”不能被多个局部成功提示掩盖。每一步应明确它已经证明了什么、还没有证明什么，以及接下来如何完成。

外网不可达可能来自 NAT、防火墙或运营商网络，产品无法保证自动修复，但必须能表达未知、定位到可检查的层次。不得未经同意开放端口、修改防火墙或设置隧道。

### 3.3 默认值体现判断：不能把所有选择都交给新手

创建流程先询问游戏版本和用途，再给出有依据的推荐。Java 根据 Minecraft、服务端及受支持组合选择；内存建议考虑宿主可用资源，避免从固定档位推导“支持多少玩家”的保证。

推荐必须说明原因，允许高级用户查看和调整。默认值不能隐藏许可接受、安全边界或不可逆影响；EULA 仍需明确操作。

若缺少合适 Java，第一版至少提供针对当前平台和版本的准确安装步骤、完成后重新检测入口。托管 JDK 下载只有在这一步被证明是主要流失原因时，才进入下一轮范围。

### 3.4 简洁来自删减决策，不是隐藏状态

默认界面优先回答四件事：当前管理哪台服、它是否可用、是否有必须处理的问题、现在最合理的操作是什么。

世界与实例是用户对象；任务、事件、列表查询和恢复 token 是实现对象。内部任务可以持久化，但“刷新列表完成”不应挤掉“备份失败”的重要性。需要重新分配展示层级，而不是为了界面干净删除审计能力。

默认可见的主要动作建议不超过三个。这是需要试用验证的设计约束，不是宣称已有研究证明的通用数值。键盘快捷方式、命令和鼠标可以并存，但同一操作必须进入相同的业务行为。

### 3.5 质量由最弱的关键环节决定

下载动画再流畅，也不能抵消默认安装失败。状态文案再精致，也不能抵消恢复结果不可信。已经存在的严重失败，不得靠“alpha”标签合理化。

允许未完成的功能被明确列为实验能力；不允许把未完成的结果显示成完成。正确性、世界安全和进程身份没有“先上线再说”的例外。

### 3.6 形成自己的语言与身份

Claude、Codex、PCL 等参考可以帮助探索，但成熟产品需要围绕 Minecraft 服主形成自己的信息层级和词汇。借鉴交互效率，比长期依靠其他产品名称表达品质更重要。

下一阶段选择一个默认视觉方向，保留必要的高对比/低彩色表现，暂停新增主题和装饰动画。现有主题的兼容与缺陷修复继续进行；是否减少主题或经典视图，应先确认实际用户和迁移成本。

不要将“Apple 风格”理解为白色、大留白、特定字体或模仿系统控件。终端场景的品质体现在键盘操作、状态可读性、响应一致性和失败恢复。

## 4. Minecraft 场景必须尊重的现实

| 现实 | 产品决策 |
| --- | --- |
| 客户端、服务端、加载器、扩展存在兼容关系 | 创建与加入说明明确精确版本；“最新版”不能代替兼容选择 |
| Paper 与 Vanilla 的行为可能不同 | Paper 作为首个完整路径，但不能宣传为严格原版；技术生存用户需要清楚边界 |
| 存档积累不可替代 | 验证备份、恢复并实际进入世界核对；程序回滚与世界降级分别描述 |
| 客户端整合包不等于服务端包 | 优先作者提供的服务端包；未知 mod 不按名称猜测删除；通用转换暂缓 |
| 外网连通性受部署环境影响 | 分层检查服务、局域网、外网；明确“未验证”，不给虚假的绿色联机结论 |
| 插件/mod 更新可能破坏兼容 | 下载成功不等于启用成功；后续更新能力需具备预览、备份、首次启动验证 |
| 玩家需要长期运行，停服有成本 | 首轮把停服备份流程做好；根据实际停服负担决定在线/定时备份优先级 |
| 国内用户可能遇到上游访问困难 | 测量真实失败率，提供来源与重试说明；代理/镜像不得绕过可信元数据与校验规则 |

## 5. 立即冻结、继续维护与下一版交付

这里的“冻结”指暂停新增范围，不是删除已交付能力或拒绝修复问题。

| 决策 | 范围 | 原因或解冻条件 |
| --- | --- | --- |
| 下一版主交付 | Paper 从安装到实际联机的完整旅程 | 直接兑现首个用户承诺 |
| 下一版主交付 | 少量常用配置编辑、可靠保存、受控重启 | 用户开始日常使用后立即需要 |
| 下一版主交付 | 常见启动失败诊断和明确任务结果 | 减少必须找维护者求助的情况 |
| 继续维护 | Fabric、已有扩展/包导入、多页面、现有主题 | 已有功能不应失管；暂不扩大承诺 |
| 暂停新增 | Forge/NeoForge/Quilt、任意客户端包转换 | 等首个闭环通过、且有真实需求和隔离验证能力 |
| 暂停新增 | AI 自动修复、模型接入、多节点编排、多用户账户 | 当前不能解决主要旅程断点，还会增加执行与支持边界 |
| 暂停新增 | 主题数量、装饰性面板、重复入口 | 先证明必要状态可见、操作可发现 |
| 按证据推进 | 接管旧服、在线/定时备份、托管 JDK、代理 | 用迁移阻力、停服成本和安装/下载失败记录排序 |
| 独立质量工作 | 升级前任务保护、平台服务验证、分发信任 | 随发布级别设门槛；不能以新功能挤掉必要安全工作 |

Vanilla 等原有首版承诺若后移，应同步调整路线图并解释原因。不能在宣传保持“首版支持”的同时，内部悄悄删掉验收项。

## 6. 下一版：一个有边界的“朋友服可靠版”

“朋友服可靠版”是内部里程碑名称，不是已经达到稳定质量的宣传用语。

### 6.1 唯一主旅程

```text
安装并打开
  → 检查环境，缺项有可执行修复入口
  → 创建 Paper 实例，版本与朋友客户端一致
  → 启动并验证 Minecraft 服务响应
  → 展示适用于当前网络的加入说明
  → 用户与朋友实际进入游戏
  → 修改日常配置，明确何时生效
  → 有意识地停服、备份、恢复并核对世界
  → 关闭界面、重新进入，仍能正确管理
```

不得把所有步骤塞进一个强制长向导。首次开服、日常维护和恢复分别设计，保留上下文并逐步显露选项。

### 6.2 配置编辑的最小范围

首轮仅覆盖 MOTD、人数上限、难度、视距等经过明确建模和测试的字段。每个字段解释用途、有效值和生效方式。

保存前展示差异；保留未知键和注释；检测外部修改；失败保留旧文件；需要重启时显示待应用状态。重启需明确说明停止保存与再次就绪两个阶段，第一阶段失败不能继续启动第二个进程。

端口涉及实例元数据同步，世界生成参数涉及已有世界语义，认证设置涉及身份和安全边界，应另行设计，不能混入通用表单顺手开放。

### 6.3 诊断的最小范围

覆盖 Java 不匹配、端口占用、EULA 未接受、典型加载依赖失败等可提供可靠证据的问题。诊断输出包含发生了什么、证据位置、建议操作和不能确定的部分。

无法确定内存不足或模组冲突时，给出候选与证据，不将日志关键词当作确定根因。首轮不做自动修改系统环境、自动删 mod 或自动重启循环。

### 6.4 日常备份的最小范围

先把“当前运行中，备份需要停服”的原因和路径说明白。可以设计有明确确认的停服后备份流程，但是否恢复运行由计划和用户意图决定。

成功需要文件提交与校验成立；失败必须留下可见结果。恢复前明确备份时间、世界范围、覆盖影响以及当前世界如何保留。若没有自动保存当前世界，必须明确说明，不能暗示恢复可一键撤销。

## 7. 交互质量：不接受的表现与替代标准

视觉层级、输入/焦点和关键页面的专项分析见 [UI 与交互评审](UI_UX_REVIEW.md)，其中区分当前代码问题、历史截图观察和待实测风险。

| 不接受的表现 | 替代标准 |
| --- | --- |
| “已加入队列”使用与“备份成功”相同的成功结论 | 接受、执行中、成功、失败、取消分别表达，结果到达后更新 |
| 标题说已就绪，底部仍说等待启动 | 当前状态采用同一事实；历史反馈明确属于历史 |
| 失败后 spinner 无限转，用户只能退出 | 加载结束，保留输入，显示修复或重试入口 |
| 把 `127.0.0.1` 当作通用分享地址 | 明确本机、网络候选地址和外网验证状态 |
| 页面只剩一段错误码或实现术语 | 先说明影响和下一步，技术证据可展开 |
| 提交恢复时只问“确定吗” | 显示实例、备份时间、覆盖范围及明确确认动作 |
| 未知进程被当成已停止 | 显示身份未知，阻止有风险的操作，提供检查说明 |
| 小终端截掉当前对象或危险操作影响 | 缩减装饰与次要信息；无法安全完成时明确要求更大空间 |
| 颜色是唯一的失败提示 | 文字、符号与焦点共同表达；`NO_COLOR` 下仍可理解 |
| 输入框既收管理命令又收控制台命令，但没有对象提示 | 始终展示目标实例和输入语义；无明确目标时不发送 |

80×24 为主要可用性验收尺寸；40×12 做安全退化检查，不强行承诺相同信息密度。键盘全流程可达，状态文字不能依赖微弱对比度，动画可减少且不承担唯一信息通道。

## 8. 发布门槛与一票否决

以下为建议采用的门槛，数值用于团队决策，尚无本项目实验数据证明其最优。达到小样本门槛只能支持下一轮验证，不能作为总体成功率的统计保证。

### 8.1 候选版本的四道门

| 门 | 所需证据 | 未通过时的处理 |
| --- | --- | --- |
| G0：工程与契约 | 受影响测试、workspace 门禁、协议窗口、文件安全与失败恢复检查 | 不进入用户试用 |
| G1：真实端到端 | 固定候选产物，在支持矩阵内完成安装、客户端加入、重连、备份恢复 | 修复或收紧公开支持范围后重验 |
| G2：独立用户 | 5 名目标用户只依赖发布文档，至少 4 名无需开发者指导完成创建到本人加入；至少 3 组完成朋友加入 | 归类失败原因，返回交互或环境工作包 |
| G3：持续使用 | 其中至少 3 名服主在 7 天内主动再次使用；完成各自的维护任务，无已知未修复的数据/进程安全问题 | 不扩大发布范围，先解释流失与求助原因 |

测试环境按真实场景记录：平台、硬件、终端、Java、游戏版本、网络类型及产物版本。端到端验收使用可恢复的测试世界，不拿唯一生产存档冒险。

“10 分钟开服”暂作为待验证目标。计时应同时记录下载等待、环境准备、用户决策和操作耗时；不能删去网络和 Java 安装时间后对外宣称完整流程只需十分钟。未成功样本也必须计入记录。

### 8.2 任意一项成立，阻断对应候选版本发布

1. 可复现的世界损坏、错误恢复或未经确认覆盖数据。
2. 错误标记备份成功，或 hash/事务失败后仍允许把结果当成已验证备份。
3. 操作发往错误实例、终止身份未验证的进程，或重复启动造成双进程。
4. 在声明支持的环境中，默认安装或主要开服路径不可完成且没有准确边界说明。
5. 常见失败没有结果反馈，用户无法判断是否完成、是否仍在运行。
6. 升级会打断敏感写入却没有明确的阻止、等待或恢复策略。
7. 页面、安装说明或发布说明对该候选产物作出无法证实的重要能力承诺。

内部测试可以在风险受控、问题已记录的情况下继续；不可把仍有否决项的产物宣传为稳定可用。发布日期不能成为豁免数据与进程安全的理由。

### 8.3 Alpha 与稳定发行的区别

Alpha 可以明确限定用户、场景和实验能力；不能降低结果真实性要求。稳定发行还应有支持矩阵、可追溯构建、可靠分发真实性验证、升级/回退演练和用户支持路径。

哈希校验不能单独证明发布者身份；签名或可信发行渠道必须与对应威胁模型匹配。macOS 公证、Linux 包分发等按所选渠道建立验收，不借用平台名义声称已经获得认证。

## 9. 衡量结果，而非活动量

| 指标 | 明确定义 | 不能替代它的数字 |
| --- | --- | --- |
| 首次游玩成功 | 目标用户从候选产物安装后，使用真实客户端进入所建服务器 | 下载完成数、进程启动数 |
| 朋友加入成功 | 在记录的网络条件下，另一位玩家实际进入 | 端口探测、本机 Server List Ping |
| 独立完成比例 | 无维护者额外指导完成的用户数 / 所有有效试用用户数 | 演示录像或作者熟练操作 |
| 支持负担 | 每名用户求助次数、原因、解决时间，含放弃案例 | issue 总数下降 |
| 恢复可信度 | 恢复后进入游戏，核对预设世界标记及约定玩家数据的结果 | 仅文件复制成功 |
| 持续价值 | 用户因真实需求再次开服或维护，而非按测试要求点击 | star、主题数、命令数 |

初期用用户同意的观察记录和脱敏报告收集证据即可，不必先建设遥测平台。不要默认上传聊天、玩家身份、地址、token 或完整配置。

为验证差异化，可用同样任务比较 mctl、mcman 和一个网页面板。比较操作成功、恢复能力、学习成本和支持负担；不能仅凭功能列表或 star 宣称更好。

## 10. 执行方式：四个阶段，按出口推进

### 阶段 A：收紧承诺，建立一个事实版本

- 指定一名对“用户完整成功”负责的负责人，小团队可由同一人承担。
- 选定候选产物与支持矩阵，区分已发布、当前开发和计划能力。
- 对照 README、FAQ、官网、帮助和发布说明；保留准确的历史说明，为当前文档标明适用版本。
- 复验历史体验报告，记录已修复、仍存在和未覆盖的问题。

**出口**：能回答当前版本到底给谁用、能完成什么、有哪些已知限制，以及每个结论的证据。

### 阶段 B：完成唯一主旅程

- 先修真实体验中的阻断、状态误导和错误反馈。
- 实现最小配置保存/应用闭环及基础诊断。
- 验证实际客户端、朋友加入、停服备份与恢复。
- 工程改动集中在配置可靠保存、异步响应归属、任务结果和实例操作边界。

**出口**：G0、G1 通过；不依靠临场改配置、临时 shell 命令和开发者解释掩盖流程缺口。

### 阶段 C：让独立用户决定是否完成

- 招募少量目标用户，先观察，不替他们操作。
- 记录卡点和错误理解，按问题模式修复，不按单个用户建议无限加功能。
- 对阻断问题使用新候选版本重测，避免把不同构建的零散成功拼成一次验收。

**出口**：G2、G3 通过；不通过则收缩承诺或修复，暂不解冻扩张。

### 阶段 D：选择下一项真正需要的能力

根据试用证据只选一个重点：已有服主迁移被阻断则做接管旧服；长期运行无法接受停服备份则研究在线/定时备份；环境准备是主要流失原因则做托管 Java；目标用户确有原版机制需求则补 Vanilla。

Fabric/整合包要成为下一主线，至少需要真实包样本、版本兼容策略、隔离首次启动和失败报告。AI 要进入产品，必须先证明确定性诊断无法覆盖的需求，并有受限操作模型。

## 11. 工程投入必须对应产品验收

[工程优化指南](ENGINEERING_OPTIMIZATION_GUIDE.md) 负责实现方法，本文负责决定什么值得先实现。

| 工程工作 | 必须说明的用户收益 |
| --- | --- |
| 收敛 TUI 状态与请求身份 | 切页后不串实例，状态不矛盾，失败后能继续操作 |
| 配置读写与事务治理 | 设置不会悄悄丢失，保存失败不破坏已有配置 |
| 下载与包处理边界 | 错误来源和不兼容内容不会进入可启动实例 |
| 文档与发布能力统一 | 用户安装到的版本符合说明，减少无效排障 |
| 删除重复实现与死文件 | 规则只有一个权威位置，改动更少遗漏，发布资产完整 |

可以为这些结果进行必要重构；不能以“高级架构”“更像 Apple”或“全部遵循 DRY”为理由开启无限期重写。大文件行数下降不是用户验收，代码总量减少也不是自动胜利。

## 12. 每次产品评审只回答七个问题

1. 这次服务的是哪位用户、哪个具体时刻？
2. 用户原本无法完成什么，现在能完成什么？
3. 我们删掉了哪些不必要选择，默认判断依据是什么？
4. 正常、失败、中断和恢复路径是否都能说明白？
5. 结果由什么事实证明，是否只是 UI 或任务状态自我宣称？
6. 新增维护面值得吗，需要暂停哪项已有计划来承担它？
7. 如果明天交给陌生用户，团队愿意对哪些承诺负责？

答不清楚，就不进入开发。发现跨实例、数据安全或真实性问题，就不进入发布。只有真实使用证明现有范围已完成，才扩大产品范围。
